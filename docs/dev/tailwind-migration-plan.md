# Total migration: Bootstrap + react-bootstrap → Tailwind CSS v4 + Base UI

## Context

stacker.news is a Next.js (pages router) app styled with Bootstrap 5.3.8 + react-bootstrap 2.10.10 + SCSS. Goal: remove both completely, rebuild components on **@base-ui/react 1.6.0** (NOT preinstalled — installed in PR2 commit 0; the old `@base-ui-components/react` package name is dead) styled with **Tailwind CSS v4.3.1**. **Strategy revised 2026-07-06 (was: pixel-identical to master)** — behavior parity stays binding; visual parity does not. Components are built with **native Tailwind/Base UI solutions at nearest-native values**, with SN's identity carried by a small `@theme` brand block instead of value-exact Bootstrap replication (see §Strategy revision below). Dark mode, territory runtime branding (CSS-var overrides from `lib/domains/custom-css.js`), and all interaction behavior must survive unchanged.

Current state: **PR1 shipped** (infra + dual theme attribute + codemod sweep — summary below) and **PR2 in progress** on `redesign-base-ui-components`; the live execution log is [pr2-base-ui-components.md](./pr2-base-ui-components.md) §0. The original census is `docs/dev/bootstrap-usage-audit.md` (160 distinct utility classes / 1527 uses; undercounted — wallets/ and `groupClassName`-style props add ~170 more).

**Decided with user:** 3 PRs — ① Tailwind parity, ② Base UI components, ③ Bootstrap removal. Latest versions of everything. Token rename `--bs-*`/`--theme-*` → `--sn-*` and `data-bs-theme` → `data-theme`. The 63 `.module.css` files stay (var re-point only); Tailwind-ify opportunistically later. PR2 components use **hybrid styling** — module.css for stateful skins/variants, Tailwind for layout (keystone 6).

## Strategy revision (2026-07-06) — native-first, no pixel parity

Decided with sox after C2's first four components landed with "ugly tw values" (arbitrary brackets replicating compiled Bootstrap). In one sentence: **stop replicating Bootstrap's compiled output — use the nearest native Tailwind/Base UI solution, with SN's identity carried by `@theme` tokens.** Behavior parity stays binding; visual deltas from native values are accepted, judged by eye in light + dark + branded territory. The binding rules live in keystones 5 (motion) and 6d (values); the one deliberate type token is `--text-base: .93rem` + `--text-base--line-height: 1.75`. Executed same day as **C2.5** (component recipes reworked, tree swept, codemod map updated) — as-built log in the PR2 doc §0. Explicitly untouched by the revision: the coexistence cascade (keystone 1 — the `important` flag out-shouts Bootstrap while both load; it is not a parity mechanism), the `--sn-*` bridge, wrapper APIs, the C-commit order, deviations D1–D10, and the interaction-parity checklist. The visual-diff harness survives as a review aid, not a pixel gate.

## Architecture keystones (apply to all 3 PRs)

1. **Cascade-layer coexistence.** Bootstrap CSS is unlayered with `!important` utilities. Tailwind utilities import with the `important` flag: *layered `!important` > unlayered `!important` > unlayered normal > layered normal* (CSS Cascade 5). This reproduces Bootstrap's "utilities always win" contract during coexistence. **Keep the flag through PR3 and its parity gate** — dropping it *alone* would flip every utility-vs-module conflict. But it is scheduled debt, not permanent architecture (revised 2026-07-05 after PR2 §11.0 exposed its failure mode against consumer module skins): the post-migration **cascade de-escalation** cleanup drops it *paired* with wrapping module skins in `@layer components`, which preserves the utilities-win contract without any `!important`.
2. **Alias-flip token bridge.** PR1: `--sn-primary: var(--bs-primary)` etc. (aliases point at live Bootstrap vars, so territory branding + dark mode work untouched). PR3 flips direction: `--sn-*` become canonical literals, `custom-css.js` emits `--sn-*`, everything else renames mechanically.
3. **Dual theme attribute.** PR1 makes the `_document.js` init script + `dark-mode.js` set BOTH `data-bs-theme` and `data-theme`. PR3 drops the `bs` one.
4. **Wrappers keep their public APIs.** `useShowModal` (21 files), `useToast` (34), `form.js` exports (~100 consumers), `ActionDropdown` (13) — internals swap, consumers don't move. New compound components mirror react-bootstrap prop shapes (`variant`, `size`, `as`→`render`) so consumer diffs are import-line swaps.
5. **Subtle native motion (revised 2026-07-06; was "no animations").** Master snaps only because Bootstrap compiled with `$enable-transitions: false` — a parity artifact. New popups (menu, tooltip, popover, dialog, drawer, collapsible) adopt Base UI's native pattern: ~150ms ease-out fade (+slight scale where the Base UI docs examples use it) via `data-starting-style`/`data-ending-style` CSS in the popup chrome modules, disabled under `@media (prefers-reduced-motion: reduce)`. Toast slide/progress keeps its existing keyframes; Drawer's 450ms default is shortened to match the ~150ms family, not zeroed.
6. **Hybrid styling split (PR2+).** Module CSS answers *"what does this component look like in each of its states"*: variant skins (`data-variant` + CSS-var indirection), state styling via Base UI data attributes (`[data-highlighted]`, `[data-popup-open]`, `[data-disabled]`…), popup chrome/shadows/z-index, the surviving animations. Tailwind answers *"how is this instance arranged on the page"*: layout, spacing, flex composition, and all consumer `className` overrides — which always win, because utilities are layered-`important` and modules are unlayered normal (keystone 1). Safety rules: **(a) one property, one source, per component** — `twMerge` is blind to module classes, so never declare the same property in both the module skin and the recipe's utility string; **(b) modules stay unlayered until the post-PR3 cascade de-escalation** — layering them (or dropping the utility `important` flag) *on its own* flips the override contract; the two moves only work as a pair (see post-migration cleanups); **(c) new modules theme via `var(--sn-*)` only** (aliases live since PR1) — dark mode and territory retint flow through with zero `[data-theme=dark]` selectors, and the PR3 rename sweep never touches these files. Button (mapping table) is the template. **(d, added 2026-07-06)** Values rule: recipe utility strings and new module declarations use native-scale classes or brand tokens only — no arbitrary bracket values except deliberate SN one-offs (e.g. the alert border-radius). Nearest-native supersedes value-exact everywhere.

### Post-migration cleanups (AFTER PR3, not part of it — tracked here so they aren't lost)
- **Kill the `-rgb` triplet machinery.** The triplets exist only for `rgba(var(--*-rgb), a)` — modern CSS gets the same result from the canonical var: `color-mix(in srgb, var(--sn-*) ⟨a·100⟩%, transparent)` (exactly what Tailwind v4 opacity modifiers compile to; visually identical). Census 2026-07-05: 13 uses — `--theme-color-rgb`×6 (wallet theming), `--bs-danger-rgb`×4, `--bs-primary-rgb`×2, `--bs-warning-rgb`×1 — in globals.scss (→ whatever survives into app.css) + 5 `wallets/client/components/**` module.css files. Rewrite those, then stop emitting `-rgb` from `custom-css.js` and `tokens.css`, and delete `hexToRgbTriplet` from `lib/color.js`. Do NOT do this during PR3 — the rename sweep keeps `rgba()` forms working and parity stays trivially provable.
- **(companion, same family)** Replace the YIQ `getContrastTextColor` with CSS `contrast-color(var(--sn-primary))` behind `@supports` once Chrome/Firefox ship it (Safari-only as of 2026-07). Flip threshold differs from YIQ for edge colors — an intentional visual change, so strictly post-parity.
- ~~Tokenize recurring arbitrary values in one sweep~~ **Superseded by the 2026-07-06 strategy revision** — arbitrary values are eliminated *during* PR2 (C2.5 sweep) rather than tokenized after: `--text-base: .93rem` is the one deliberate type token, everything else snaps to the stock scale, and buttons/inputs agree on shared control metrics by both using native steps (`py-2 px-4`-family) instead of a shared `0.42rem` token. Still true and binding for any future custom token: it needs a matching `lib/cn.js` classGroups entry (tailwind-merge is blind to custom names; unknown `text-*` is misclassified as a color). Distinct from PR4 (below), which reconciles *old Bootstrap-era* values SN may want back — not mid-migration arbitrary brackets.
- **Cascade de-escalation — retire the utility `!important` regime (diagnosed in PR2 §11.0; decided 2026-07-05).** The `important` flag on the utilities import exists only to out-shout Bootstrap's unlayered CSS; once Bootstrap is gone it is pure debt with a silent failure mode — a stray `text-*`/`bg-*` utility in a recipe or at a call site beats even `!important` module skins (layered-important > unlayered-important) and freezes component/state styling while the default state looks fine. Two flips that MUST land together in one commit (each alone inverts the override contract, per keystones 1/6b):
  1. drop `important` from the utilities import in the Tailwind entry;
  2. wrap component-skin module CSS in `@layer components` — the PR1 layer order (`theme, base, components, utilities`) already reserves the slot; mechanical per-file wrap or a postcss step.
  Result: normal-vs-normal everywhere, utilities still beat skins because `utilities` declares later, consumer `className` overrides keep winning, zero `!important` in app CSS. Same-commit follow-ups: (3) sweep for shout-skins that override another component's module base — the two known badge ones (`item.module.css .newComment`, `notifications.module.css .badge`) were **already absorbed into `ui/badge.module.css` as the `.grey` variant during PR2 C2 (2026-07-06)**, so for badge this is now a verification grep rather than a conversion; any survivor's `!important` would out-rank normal utilities post-flip and recreate the old trap in mirror image (re-census as later C-commits land); (4) audit remaining module `!important`s (e.g. fee-button's tfoot border) — keep only same-component pins — and adopt the ownership rule going forward: **module CSS never overrides another component's module CSS; cross-component customization goes through `var(--sn-*)` writes or call-site utilities.** Caveat to census before shipping: third-party CSS that stays unlayered (react-datepicker; react-select until C13) currently *loses* to layered-important utilities and would *win* against layered-normal ones — find utility-vs-third-party conflicts first (SN's own third-party restyles live in unlayered app CSS and are unaffected). Verify with the §Verification pixel harness at ~0 diff. Once landed, PR2 §11.0 collapses to one sentence: modules define the component, utilities and vars customize the instance, utilities win.

## PR4 — SN identity reconciliation: audit Bootstrap-era values, port the keepers (scope requested by sox 2026-07-07)

Native-first (§Strategy revision) ships PR2/PR3 on stock Tailwind values, accepting deltas commit-by-commit — but nobody has yet judged the *sum* of those deltas against SN's old identity. PR4 is that deliberate pass: review every Bootstrap-era custom value and override — typography, spacing, radii, shadows, colors, component metrics — and per value either **ratify the native replacement** (the default) or **port the old value back as a named token**.

Why PR4 and not inside PR3: PR3 must stay mechanical (rename/delete with parity trivially provable — folding design judgment into it poisons that gate), and "does native read right?" can only be judged against the fully-native app, which first exists after PR3 lands. Ordering vs the post-migration cleanups above: none — this pass changes *values*, those change *cascade mechanics*; run whichever is ready.

**Inputs — pin them, PR3 deletes the sources:**
- `globals.scss` at the PR2 merge commit (a git ref suffices): the `$variable` override block is the census universe (`$grid-gutter-width: 2rem`, `$font-size-base: .93rem`, `$btn-*`, radii, RFS settings, …).
- The PR3 Step-0 computed-style dump (captured for base.css; doubles as the "what Bootstrap actually painted" record).
- [bootstrap-tailwind-tokens.md](./bootstrap-tailwind-tokens.md) — the sass-compiled derivation tables; historical for PR2, promoted to PR4 census input.
- The logged intended deltas: PR2 doc §0 C2.5 (the value sweep + "left as deliberate one-offs" list), §11.4's "behavior parity, not pixel parity" bullets, and PR3's base.css design choices (h1–h6 on stock steps, RFS fluid clamps dropped).

**Method:** one census table — old painted value | native value now shipping | verdict (ratify / port). Default verdict is ratify; port only what carries SN identity and visibly reads wrong at native — this is a design pass, not a parity restoration (that strategy stays dead). Every ported value lands as an `@theme` token on the `--text-base` pattern (with paired companions like `--*--line-height` where the scale carries them), **plus the mandatory `lib/cn.js` classGroups entry** (C0 rule — tailwind-merge misclassifies unknown custom classes and overrides silently stop merging), plus a sweep replacing the native utility at consuming sites. No arbitrary brackets — keystone 6d still binds; ports become named tokens or they don't happen.

**Candidate buckets (census targets, not commitments):** heading scale vs the old RFS fluid clamps; secondary type sizes (small/hint/muted); control metrics — button/input paddings deliberately share native steps since C2.5, so changing either side re-opens the C9a InputGroup alignment contract (change both or neither); radii (`rounded-md` 0.375rem vs Bootstrap's 0.4rem — the C1 territory-header correction proved this delta can be visible); shadows/borders; any color that slipped past PR3's `tokens.css`.

**Gate:** §Verification eyeball pass on affected screens (light + dark + branded territory) + the classGroups check for every new token.
